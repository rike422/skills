# Validation and Release Procedure

## 1. Inspect Before Mutation

```bash
git status --short
apm --version
apm install --help
apm lock --help
apm update --help
```

Read the current manifest and lock diff before accepting generated changes. Version output belongs in the verification report when command compatibility matters.

## 2. Validate Skill Structure

For each changed Skill, use the repository-built evaluator:

```bash
node tools/skeval/dist/cli.js validate skills/<name> --agent claude
```

This checks suite structure and paths. Run live behavioral evaluation only when the change risk and available agent runtime justify it; do not confuse schema validation with behavioral proof.

## 3. Resolve and Preview

For the currently verified APM 0.29 CLI:

```bash
apm lock --target claude,cursor,codex
apm install --dry-run --target claude,cursor,codex
```

Inspect `apm.lock.yaml` for the expected Skill set and relative source identities. If `apm_modules/` or target directories appear in the repository, first verify they were generated by this run, then remove only those exact generated paths. Never use a broad cleanup command.

## 4. Prove Deployment in an Isolated Consumer

Dry-run verifies resolution, not written output. To verify deployment without touching user scope:

1. Create a temporary directory and a consumer subdirectory.
2. Make the consumer directory the shell working directory.
3. Run `apm install` there with absolute paths to each repository Skill and an explicit `--target claude,cursor,codex`.
4. Inspect the temporary consumer's `apm.yml`, lockfile, `.agents/skills/`, and any Claude compatibility output produced by the installed version.
5. Verify the source repository manifest and status did not change unexpectedly.

Conceptual example, with paths replaced by exact validated values:

```bash
cd /tmp/exact-apm-check/consumer
apm install \
  /absolute/repository/skills/first-skill \
  /absolute/repository/skills/second-skill \
  --target claude,cursor,codex
```

Do not instead stay in the source checkout and rely only on `--root /tmp/...`. APM still resolves sources and mutates package declarations relative to the current working directory.

Do not use `--global` for this test.

## 5. Audit the Commit Boundary

Stage explicit paths, for example:

```bash
git add \
  skills/<name> \
  apm.yml \
  apm.lock.yaml \
  README.md
git diff --cached --check
git diff --cached --stat
git diff --cached
```

Scan the staged diff for credentials, tokens, private keys, and machine-specific home paths. Confirm unrelated modified, deleted, or untracked files remain unstaged. Use `git diff --cached --name-only` as the source of truth for commit scope.

Commit only after explicit authorization. Use an English conventional subject prefix and a Japanese body when needed. Never push as part of routine validation; pushing is a separate external publication action.

## 6. Report Availability Honestly

After a local commit, say that source-checkout installation is verified and public subdirectory installation becomes available after push. After an authorized push, public commands can be reported as available at the pushed ref.
